# 逻辑数据入湖（数据编织）技术可行性调研报告

> 版本：v1.0（修订版）　编制日期：2026-09-22
> 范围：开源方案、国内商用产品（信创视角）调研对比，以及基于 Trino 的选型论证与验证方案
> 说明：商用产品的功能与名录信息会随版本变化，正式选型前需按厂商最新资料与《安全可靠测评结果公告》复核。

---

## 0. 摘要

- “逻辑数据入湖”本质是**不搬数据、按需联邦/虚拟化查询**：湖（对象存储 + 开放表格式）作为统一访问面，源系统保留数据主权，查询时下推、跨源 JOIN 由引擎完成。
- **数据编织（Data Fabric）= 数据虚拟化/联邦查询引擎 + 元数据（主动元数据）+ 治理（权限/脱敏/血缘）+ 语义层 + 按需物化加速**。虚拟化是“发动机”，编织是“整车 + 交通规则”。
- **关键约束（安可名录）**：安全可靠测评（“国测”）覆盖品类为 CPU、AI 芯片、操作系统、数据库、打印机主控芯片——**数据库被强约束**，而**查询中间件不在该名录品类内**。因此把“联邦/虚拟化引擎”做成数据库形态、或用某款数据库当引擎，会被名录收敛；用 **Trino 这类中间件**更契合逻辑入湖的“连接与编排”本质。
- 国内商用可重点看**大应数据 Aloudata（AIR 逻辑数据编织平台 + BIG/CAN/Agent）**、星环 Transwarp、华为云 DataArts Studio、阿里云 DataWorks、百分点/数猎天下等。
- 我们已用 **Trino 483 + 自研连接器**验证：跨 **OceanBase / Greenplum / 达梦** 单 SQL JOIN、动态 Catalog、表级权限、元数据发现、查询工作台，端到端 `E2E_OK`。**“基于 Trino 自研”在功能上成立且可扩展。**
- 结论：推荐**“Trino 自研为联邦底座 + 按需外采/自建治理与语义层”**的组合路线。

## 1. 概念与定位

逻辑入湖与物理入湖的区别：

```
物理入湖 (ETL/ELT)                逻辑入湖 (Virtualization/Federation)
┌────────┐  ┌────────┐            ┌────────┐  ┌────────┐
│ 源A DB │  │ 源B DB │            │ 源A DB │  │ 源B DB │
└───┬────┘  └───┬────┘            └───┬────┘  └───┬────┘
    │ 抽取      │ 抽取                │ 按需查询     │ 按需查询
    ▼           ▼                    └─────┬───────┘
 ┌───────────────────┐              ┌───────▼────────┐
 │  湖/仓 (副本)      │              │ 联邦引擎(Trino) │
 └───────────────────┘              └───────┬────────┘
    数据被复制、延迟、成本高                │ 统一 SQL / 视图
                                           ▼
                                     湖/仓 (可选物化热点)
```

| 概念 | 一句话 | 关键差别 |
|---|---|---|
| 数据联邦 | 跨多个库的 SQL JOIN | 最基础，通常无治理/语义层 |
| 数据虚拟化 | 统一逻辑层 + 下推 + 缓存 | 联邦 + 语义/缓存/安全 |
| 数据编织 Data Fabric | 虚拟化 + 元数据 + 治理 + 主动元数据 | 面向企业规模的“系统” |
| 数据网格 Data Mesh | 组织/权责范式（域自治数据产品） | 偏组织架构，可与编织互补 |
| 湖仓 Lakehouse | 存储/表格式（Iceberg/Delta/Hudi） | 逻辑入湖的“落点” |

**术语对齐**：本报告里“逻辑数据入湖”= 以湖仓为统一访问层的虚拟化/联邦；“数据编织”= 在此之上叠加治理与元数据能力的平台形态。

## 3. 开源方案调研与对比

| 方案 | 定位 | 联邦/虚拟化 | 优势 | 局限 |
|---|---|---|---|---|
| **Trino**（原 PrestoSQL） | MPP 查询中间件 + 连接器 | ✅ catalog 即连接器 | 连接器生态最广、下推成熟、插件化、Apache-2.0 可审计可控、社区活跃、可自研连接器；Iceberg/Delta/Hive 原生 | 裸引擎缺治理/缓存/语义层；跨源 JOIN 在引擎内做（数据移动）；CBO 依赖统计质量 |
| **openLooKeng**（华为开源） | 面向跨源的联邦引擎 | ✅ 跨源优化 | 国产背景、跨源优化 | 生态/活跃度不及 Trino，社区规模较小 |
| **Apache Doris / StarRocks** | MPP 数仓 | ⚠️ 外部 Catalog 联邦（Iceberg/Hive/JDBC） | 本地查询强、湖仓联邦 | 偏“仓”，跨异构实时源编排较弱 |
| **Apache Drill** | 无 schema 联邦 SQL | ⚠️ 有限 | 对半结构化数据友好 | 社区放缓、治理/并发弱 |
| **Apache Calcite** | 优化器/联邦框架 | —（库） | 被众多产品复用 | 不是成品平台，需自建 |
| **Teiid / WildFly** | 数据虚拟化 | ✅ | 开源、容器化 | 社区小、学习曲线高 |
| **DataHub / OpenMetadata / Amundsen** | 目录/血缘 | ❌（不是查询引擎） | 元数据/血缘 | 需与联邦引擎组合 |
| **SeaTunnel / Flink CDC / Airbyte** | 数据集成（物理搬运） | ❌ | 同步/CDC 强 | 属物理入湖，非逻辑层 |

> 关键结论：**开源成品主要就是 Trino（可自研/可控）**；治理/目录/语义层需另配，这正是“编织”的缺口，也是自研的着力点。

## 6. 方案论证：基于 Trino 自研 vs 外采商用产品

### 6.1 约束前提：安可名录的适用范围

安全可靠测评（业内称“国测”）由中国信息安全测评中心与国家保密科技测评中心联合发布。**测评品类为：CPU（含 AI 加速）、AI 训练推理芯片、操作系统、数据库、打印机主控芯片。** 截至 2026 年第 2 号公告（2026-05）已发布四批数据库名单，**有效期三年**，且条目是**具体产品与版本**（如：达梦 V9 集中式 Ⅱ级、达梦分布式 V9 Ⅱ级、OceanBase 集中式 V4 Ⅰ级、GaussDB、GoldenDB、崖山、Transwarp ArgoDB V6 Ⅰ级、GBase 8c 等）。

```
安可名录覆盖范围
┌──────────────────────────────────────────────┐
│ CPU/AI芯片 │ 操作系统 │ 数据库 │ 打印机主控芯片 │
└──────────────────────────────────────────────┘
                 ▲
                 │ 数据库被强约束（品类/版本/等级/有效期）
                 ▼
   若“联邦/虚拟化引擎”做成数据库形态 → 被名录收敛
   查询中间件（Trino 等）不在该名录品类内
```

### 6.2 为什么不宜用“基于数据库”的方案

1. **名录收敛与版本绑定**：数据库引擎必须落在名录内，且是特定产品 + 版本 + 等级；升级/换代可能触发重新评估，架构被单一数据库厂商绑定。
2. **定位错配**：数据库擅长“存 + 本地算”，对**异构源联邦、跨源实时 JOIN、API/NoSQL/对象存储接入**能力弱；逻辑入湖要的是“连接与编排”。
3. **“不搬数据”与其本性冲突**：数据库方案容易滑向“再建一个集中库”，重走物理入湖老路。
4. **自主可控与接口开放**：数据库联邦层难以自研连接器、难以透明替换；而 Trino 插件化可自研（我们已用达梦连接器验证）。

> 反过来看：**名录内的数据库**（达梦/OceanBase/GaussDB/GBase 等）**应当是“被联邦的源”，而不是“联邦引擎”**。这正好把引擎与数据源解耦。

### 6.3 中间件（Trino）为什么更合适

- **不在安可数据库名录品类内** → 不受“必须选名录数据库当引擎”的直接约束；可私有化部署、Apache-2.0 可审计可控。
- **连接器即扩展点**：可连接名录内数据库作为源，也可自研连接器（`trino-dameng` 已验证）。
- **逻辑入湖的天然形态**：coordinator 规划、worker 执行，谓词/投影/聚合下推，跨源 JOIN 在引擎内完成；湖仓（Iceberg/Hudi/Delta）可原生直读。
- **注意（风险）**：中间件自身仍需满足**信创适配**要求（国产 OS/芯片、国密、等保），但其性质是“适配与安全合规”，**不同于“必须用某款数据库”的名录硬约束**；必要时可选国产衍生（openLooKeng）或代码托管/审计方案。

### 6.4 自研 vs 外采：决策矩阵

| 维度 | 基于 Trino 自研 | 外采商用（Aloudata AIR 等） |
|---|---|---|
| 自主可控/信创 | **高**（代码可控、连接器自研、私有化） | 中（依赖厂商，私有化看产品） |
| 能力完整度（建模/加速/治理/语义） | 低（需自建） | **高**（逻辑建模、PRP 加速、行列级安全、语义层） |
| 交付速度 | 慢（引擎 + 治理都要做） | **快** |
| TCO | **低**（开源 + 自研人力） | 中高（授权 + 服务） |
| 性能上限 | 取决于下推/统计/物化（需自建加速） | 有成熟加速（如自适应关系投影） |
| 扩展性 | **强**（插件/连接器/UDF） | 受产品能力边界约束 |
| 团队要求 | 需引擎/连接器专家 | 平台使用 + 少量集成 |
| 供应商风险 | 低 | 中（锁定/服务连续性） |

### 6.5 已完成的 Trino 自研验证（实证）

| 验证项 | 结果 | 证据 |
|---|---|---|
| 版本基线 | Trino 483 引擎/镜像/客户端一致 | `version-alignment` spec |
| 跨源联邦 | OceanBase + Greenplum + 达梦 单 SQL JOIN | E2E `E2E_OK`，返回 `[[1,'alice',100],[2,'bob',200]]` |
| 连接器可扩展 | **自研 `trino-dameng` 插件**（BaseJdbcClient，SPI 483） | 日志 `Registering connector dameng` |
| 动态 Catalog | 平台注册即 `CREATE CATALOG`，停用即 DROP | 数据源生命周期 E2E |
| 下推验证 | 谓词下推（`constraint on [id]`，无 Filter） | 查询 E2E |
| 表级权限 | grant/revoke；JOIN/子查询/CTE 越权被拒 | 权限 E2E（引擎强制） |
| 元数据 | `information_schema` 由 Trino 合成（达梦无原生 info schema 也 OK） | 达梦 columns/detail E2E |
| 规模化 | 万行返回；超 `max-rows` 截断 | `[perf]` E2E |
| 工作台 | 编辑器/对象树/结果栅格/图表/历史/收藏 | `sql-editor` / `query-result-grid` / `query-history` spec |

### 6.6 待补测矩阵与路线建议

| 类别 | 待验证 | 指标 |
|---|---|---|
| 性能 | 跨源 JOIN、聚合下推、下推边界 | QPS、P95、源端负载；明确“可下推 vs 需数据移动” |
| 并发 | 1/10/50 并发 | 失败率、内存/GC，无 OOM |
| 优化器 | 统计信息质量 | ANALYZE 覆盖率、join reorder |
| 治理 | 列级权限/脱敏/审计 | 越权不可见/不可查 |
| 血缘/语义 | 与 DataHub/OpenMetadata 集成或自建 | 列级血缘可用 |
| 加速 | 热点物化（Iceberg/关系投影） | 热点查询显著加速 |
| 信创 | 国产 OS/芯片、达梦/OceanBase 适配 | 目标环境全链路可运行 |

**路线建议（分阶段）**

1. **自研 Trino 打通“连接 + 联邦 + 目录 + 基础权限”**（已完成）。
2. 视治理/加速诉求，**外采逻辑层/加速/语义组件**（如 Aloudata AIR）或自建，保持接口开放、引擎可替换。
3. 热点场景**按需物化**到湖仓，形成“虚拟化默认 + 物化加速”的混合模式。
4. 完成信创适配（国产 OS/芯片/数据库作为源）与 HA 演练。

### 6.7 结论

- **数据库方案受安可名录约束，不宜作为联邦/虚拟化引擎；中间件（Trino）不在该名录品类，天然更契合逻辑入湖的“连接与编排”定位。**
- “基于 Trino 自研”**技术可行且已实证**；“外采商用产品”（尤其 Aloudata AIR 这类逻辑数据编织平台）可在治理/加速/语义层快速补齐。
- 推荐**“Trino 自研为底座 + 按需外采/自建治理与语义”**的组合路线。
